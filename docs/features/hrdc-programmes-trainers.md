## 6a. Phase 2C, HRDC work (built 2026-10-16)

Joel's input: HRDC can raise **queries** before the training is approved, during the training, and after it's completed, and the team must attend to them. Some new programmes must be **pre-registered in the HRDC portal** and approved before they can be used for a client. Joel said "let's move on" without answering two detail questions, so these defaults were agreed (with his yes):
- Programmes live in one list (Admin work → Programmes). Anyone can quick-add a programme from the deal form, but only as "Not registered". Only Admin and Management change its HRDC status, code and dates. Deals must pick a programme from the list. Older deals keep their typed name until edited.
- HRDC query reply-by dates are typed from HRDC's email for each query, with no hardcoded deadline. "Handled by" can be any active team member and defaults to the person logging it. Admin and Management add, answer, reopen or delete queries. Reps see them read-only.
- Gate: an HRDC or HRDC + top-up deal whose programme isn't HRDC approved (or isn't picked from the list) can't tick "Apply grant". The deal panel shows why.
- Work queue: an open query is a red flag, an overdue query goes to the top, and a deal with open queries isn't "All done". A programme that isn't approved is an amber flag while the grant step is open. Programmes → "Waiting on HRDC" lists submitted programmes.
- Still to confirm with Joel: whether HRDC gives a programme code on approval (the field is optional), and who usually handles queries.
- "Verify T3 attendance" is now a built-in after-training, HRDC-only step with a file upload (2026-10-19, see section 6).
- **Programmes, course outlines and trainers belong together (Joel, 2026-10-17: "program list, course outline, trainer topics should co-relate"):** the Programme list is the master.
  - **Course outlines** have an optional `programmeId` (Joel: optional). The editor's "Programme" box picks from the list; blank = use the linked deal's programme, or none for a general outline. The course title follows the programme's name (`useProgrammeName`) unless "Type a different title". New outlines take the deal's (or the copied outline's) programme. "Start from" puts outlines of the same programme first. Logic: `outlineProgrammeId` and `resolveOutline` in `lib/outlineResolve.ts`.
  - **Trainers** have `programmeIds` ("Programmes they teach", ticked from the Programme list), which **replaced** the free-text Topics (Joel). Old `specialization` text is kept and shown as "Topics typed before" until someone removes it. The list, search and panel use the programme names.
  - **Admin work → Programmes:** each row shows deals · outlines · trainers, and the panel lists the programme's course outlines and the trainers who teach it. Delete is refused while deals or outlines use the programme; trainers who teach it get it unticked.
  - **Trainer pickers** (quotation lines, the checklist's Confirm trainer step) list the trainers who teach that programme first, marked "Teaches this programme" (`trainerOptions` in `PickOrType.tsx`).
- **Trainer links (Joel, 2026-10-17: "link and manual for now"; no AI reader, no file uploads):** a private link a trainer opens **without logging in** to fill in a **course outline** or **their own profile**. What they submit waits until the team reviews it and clicks Accept.
  - **Flow:** Alif keys the new programme on the deal (quick-add) → the team finds a trainer and ticks the programme on them → Course outline (from the deal) → **Trainer** card: pick the trainer → **Send to trainer** (the outline must be saved first) → Copy / WhatsApp the link → the trainer fills in the modules → the outline list shows "Trainer submitted: review" → **Accept into this outline** (fills it as unsaved changes; check, then Save) or **Discard** → the quotation picks up the programme from the deal.
  - **Trainers page:** **Invite a new trainer** (link for someone not in the list), **Send profile link** in a trainer's panel, and **Profiles waiting for review** at the top. The review shows each field with "Was: …"; **Accept changes** / **Add this trainer** (asks to update an existing trainer with the same name). Profile fields: name, phone, email, programmes they teach (ticks from the Programme list), other topics (`suggestedTopics`), years of experience, daily rate, bio, qualifications, past clients. The team can also edit these in the trainer form.
  - **Data:** `trainer_links/{token}` (`kind` outline/profile, `status` open → submitted → accepted/cancelled, `expiresAt` = 14 days, `submission`, who asked and decided). The token is 32 random hex characters. Rule: members read, create and update; staff delete. **Rules need publishing.** Outlines gained `trainerId`. Trainers gained `bio`, `experienceYears`, `qualifications`, `pastClients`, `suggestedTopics`.
  - **Public side:** `src/main.tsx` renders `TrainerLinkPage` for `/t/<token>` instead of the CRM. The page only talks to `serverTrainerLinks.ts` (`/api/trainer-link/get` and `/submit`, about 40 requests a minute per address). The server checks the link (exists, not cancelled, accepted or expired), returns only the programme title, the asker's first name, the trainer's own details and the programme names, and stores the **cleaned** submission (`cleanOutline` / `cleanProfile` in `src/lib/trainerLinks.ts`, with length limits; unknown programme ids are dropped). The trainer can correct and resubmit until it's accepted. No client details are shown to the trainer.
  - Tested with temporary local pages (the form on desktop and phone, submit, review and accept, invite). The server routes need the live site to test.
  - **Course outline links like "Invite a trainer" (built 2026-10-20; Joel: "a link where external trainers can fill up their course outline and preview as per original form in app"):**
    - **Course outlines → Invite a trainer to write one** (next to New outline; anyone with the outline list): optional programme and trainer, **Make the link** → Copy / WhatsApp. It's a `trainer_links` record with `kind: 'outline'`, **no `outlineId`**, plus `programmeId` and `title` (the programme name). "Send to trainer" inside an outline still works as before.
    - **The trainer's form** (`src/components/OutlineLinkForm.tsx`, used by `TrainerLinkPage` for outline links) has the same parts as the outline editor: course title, days (half days) and hours, target audience, pre-requisites, overview, learning outcomes, learning methods, modules with topics (Day picker and day titles on multi-day courses), course agenda (with "Fill in from the modules") and the optional extras. **Preview** shows `CourseOutlineDocument` exactly as the CRM prints it, with "Prepared for NEXT Academy client" on the cover; no download or print (printing shows nothing). Level and each module's duration and method are no longer asked (older submissions keep them). "Make a correction" keeps the trainer's last answers.
    - `OutlineSubmission` and `cleanOutline` in `lib/trainerLinks.ts` cover the new fields (lengths limited, half days, days per module checked against the course length, unknown fields dropped); `outlineFieldsFrom` maps a submission onto an outline, `previewOutline` builds the printed version, `outlineSummary` the one-line summary. The server's prefill for a link from an outline uses the outline's current content (`serverTrainerLinks.ts`).
    - **Review:** the Course outlines list shows **"Course outlines from trainers, waiting for review"** (invites made by the person, or all for Admin and Management in their own workspace) with **Preview**, **Accept as a new outline** (pick the deal, or a general outline) and **Discard**, and a folded **"links waiting for trainers"** list (Copy, WhatsApp, Cancel link). Accepting saves a new draft outline straight away (deal, programme from the link or the deal, trainer from the link; the course title follows the programme unless the trainer typed a different one), marks the link accepted and opens it in the editor. Inside an outline, the Trainer card's submission also has **Preview**, and "Accept into this outline" now fills in every part (and the trainer's title if it differs).
    - No rules change. Tested with a script (17 checks on cleaning and mapping) and a temporary local page (fake database and server): trainer form on computer and phone, 2-day course with the agenda filled from the modules, Preview (5 pages), Submit and correction, an older-style submission, the review box and Preview, Accept as a new outline for a deal (all fields, reference with the customer code, link accepted), the invite box, a rep not seeing another person's invites, Accept into an existing outline. The real link from a phone needs the live site.
  - **More trainer details and uploads (built 2026-10-20; Joel's list; "nothing is compulsory, just encourage them to fill up as much as possible"):** logic `src/lib/trainerProfile.ts`, fields `src/components/TrainerExtrasFields.tsx` (shared by the trainer's link page and Trainers → Add / Edit).
    - **New fields** on the trainer record (all optional): `gender` (Male/Female), `address`, `emergencyContact {name, relationship, phone}`, `languages[]` (English, Chinese, Bahasa Malaysia) + `languagesOther` (typed, after ticking Others), `trainingTypes[]` (`teambuilding`, `softskills`), `otherCerts` (next to Qualifications), `linkedin`, `youtube`, `otherSocial`, and `docs` = one file each for **Accredited TTT form** (`ttt`), **Biodata** (`biodata`), **Trainer profile** (`profile`): `{name, size, type, path, url, at, byName}`.     - **Uploads:** drop box or click, PDF / Word / JPG / PNG up to 20 MB (photo: any image, made smaller to JPEG). A trainer opening a profile link sees "We already have your biodata…" for files already on record (`onFile`; their links aren't sent). Trainer-uploaded photos print on teambuilding PDFs (`serverPhotos.ts`).
    - **Trainers screen:** review shows every new field with "Was: …" and the uploaded files; the panel shows type of training, languages, gender, topics as chips, address, emergency contact (Call), other certificates, LinkedIn / YouTube links and the three files; the list has **All / Team building / Soft skills** filter chips and type tags; search covers topics and languages. Editing saves each field whole (`mergeFields`), so removing a file on the form takes it off the record (the file stays in storage).
